# 串流片單、電影搜尋、被擋補齊 — 設計文件

日期：2026-11-11
狀態：待使用者核准
前一份設計：`2026-11-11-bilibili-full-series-finder-design.md`（已完成並合併）

標記：**〔使用者〕** = 使用者親口決定；**〔我的決定〕** = 設計者決定、可推翻；**〔待驗證〕** = 要等拿到 TMDB 金鑰實測後才能確定。

## 1. 為什麼要做

現有工具要使用者自己先知道想看哪部劇。使用者想要一個「找想看什麼」的入口：看 Netflix、HBO Max、Prime Video 上有什麼、什麼要上線，看到想看的就點一下，直接去 B 站找完整版。〔使用者〕

另外，實測發現 B 站常拒絕部分查詢，結果不齊全。使用者希望改善這點。

## 2. 目標

1. **串流片單分頁**：可切換 Netflix／HBO Max／Prime Video，看該平台**現在有的**劇與電影。〔使用者〕
2. **即將上線**：看到正要上線的劇與電影，以及上線日期。〔使用者〕
3. 片單為**美國區**。〔使用者〕
4. 點任一項 → 用它的劇名／片名直接跑 B 站完整版搜尋。〔使用者〕
5. **電影也能點去搜**，而且同樣要篩掉解說版。〔使用者〕
6. B 站拒絕部分查詢時，結果仍能變齊全——**但不繞過 B 站的防機器人機制**（見第 3 節）。

## 3. 不做的事

- **不繞過 B 站的防機器人驗證**：不偽造瀏覽器指紋或驗證票證、不代解驗證碼、不使用使用者的 B 站登入 cookie。〔設計者的硬性限制，已向使用者說明〕
- 不在工具內播放、不提供下載、不做網盤。（沿用前一份設計）
- 不顯示各平台的訂閱價格、不連到各平台播放頁。〔我的決定〕
- 不做收藏、想看清單、通知提醒。〔我的決定〕
- 不保證片單完整：只顯示各平台最熱門的部分，可往下載入更多，不是全目錄瀏覽器。〔我的決定〕

## 4. 絕對不能發生的事

- 片單資料抓不到（沒設金鑰、金鑰錯、TMDB 掛了）時顯示成「這個平台沒有內容」。必須明確說出原因與怎麼修。
- 電影搜尋把「電影解說／幾分鐘看完」當成正片排在完整版裡。〔使用者明確要求篩掉〕
- 加了電影規則之後，把原本劇集的判斷弄壞（例如一集一段的完整版被當成電影片段）。劇集的既有測試必須全數維持通過。
- 背景補齊把 B 站查到被封得更久：補齊必須很慢、有上限、會自己停。

## 5. 資料來源：TMDB

- 用 TMDB（The Movie Database）的 API。免費，但需要一組 API 金鑰。〔我的決定〕
- **金鑰由使用者自己申請**（到 themoviedb.org 註冊 → 設定 → API），貼到專案根目錄的 `config.local.toml`（已加入 `.gitignore`，不會進 git）。程式不經手註冊流程。專案附一份 `config.example.toml` 說明格式。
- 沒設金鑰時：搜尋與「最新上線」照常可用；串流片單分頁顯示設定步驟，而不是錯誤或空白。
- 取資料時要求簡體中文（`zh-CN`）片名，因為 B 站用大陸譯名；同時拿原文名。畫面兩個都顯示。〔我的決定〕
- TMDB 的各平台片單資料來自 JustWatch；TMDB 的使用條款要求標示來源，頁尾加一行「片單資料來自 TMDB 與 JustWatch」。
- 平台對應〔待驗證，建造時向 TMDB 的平台清單接口確認實際代號〕：Netflix、Amazon Prime Video、HBO Max（曾改名 Max，以 TMDB 當下名稱為準）。

### 5.1 「現在有的」

- 用 TMDB 的探索接口，條件：指定平台、地區 US、訂閱制（不含租買）、按熱門度排序。劇與電影各查一次。
- 一次載入一頁（20 部），往下捲或按「載入更多」取下一頁。

### 5.2 「即將上線」——資料有實際落差，先講清楚

免費資料來源沒有「某平台下個月會上架哪些片」的完整預告。能做到的是：

- **劇**：各平台自己出品的劇，TMDB 記有所屬電視網與首播日／新一季開播日。用「所屬電視網 = 該平台」+「播出日期在今天之後」查，日期可靠。〔待驗證〕
- **電影**：平台原創電影在 TMDB 上通常掛在該平台名下並有上映日，可查；但**授權片（別家拍的舊片）何時加入某平台，查不到**。〔待驗證〕
- 因此「即將上線」實際上是「該平台**原創**作品的即將首播」，畫面上要照實標示，不可讓人以為是完整上架預告。
- 範圍：今天起 90 天內，按日期由近到遠。〔我的決定〕
- 若實測後某平台的電影預告資料太少或太不準，該格顯示「這個平台的電影上線預告資料不足」，而不是硬湊。

## 6. 畫面

沿用現有風格（清單式已獲使用者選定；片單因為以海報辨識為主，改用海報格子〔我的決定〕）。

- 分頁列變成三個：**搜尋**｜**最新上線**｜**串流片單**。
- 串流片單分頁：
  - 第一列：平台切換（Netflix／HBO Max／Prime Video）。
  - 第二列：**現在有的**｜**即將上線**；旁邊 **劇**｜**電影** 切換。
  - 內容：海報格子，每格顯示海報、中文名、原名、年份；「即將上線」另外顯示上線日期（例如「11月28日」）與「還有 N 天」。
  - 點一格 → 切到搜尋分頁，搜尋框填入中文名，並立刻開始搜尋；搜尋框旁顯示一個小標記「電影」或「劇」，表示這次用哪一套判斷。
- 搜尋分頁新增一個**劇｜電影**切換，讓使用者手動輸入片名時也能選電影模式。預設「劇」。〔我的決定〕
- 沒設金鑰時，串流片單分頁顯示三步驟說明（去哪申請、貼到哪個檔案、重新啟動）。

## 7. 從片單點過去的搜尋

- 片單已經有中文名與原文名，所以這條路**不再問豆瓣**，直接用這兩個名字搜。
- 同時帶上類型（劇／電影）、年份、電影片長（分鐘）。

## 8. 電影的「完整版」判斷

與劇集分開的一套規則，共用同一批「解說／剪輯／學英語／網盤引流」關鍵字。

- **形式**：電影正片通常是單支影片；也可能分上下兩段、或是「系列合集」（一支影片多 P、每 P 一部）。
- **時長是主要依據**：
  - 知道片長（從片單點過去時有）：最長那一段的時長落在片長的 85%–115% → **完整**；低於片長的 60% → 排除，原因「時長遠短於片長（可能是解說）」；介於中間 → **可能不完整**，原因寫出實際與應有時長。
  - 不知道片長（手動輸入）：單段 70–240 分鐘 → 完整；40–70 分鐘 → 可能不完整；更短 → 排除。
- **系列合集**（多段、每段都像一部電影的長度）：保留，標「系列合集 · N 部」，只要其中一段符合片長就算完整。
- 標題含解說類字眼的，一律排除，不看時長。〔使用者：要篩掉解說版〕
- 標題同時含片名與年份不符的另一部同名電影時無法分辨，接受。
- 以上門檻數值為〔我的決定〕，以實測樣本調整。

**風險照實說**：電影沒有「集數」可以交叉驗證，判斷只能靠時長與標題字眼，誤判會比劇集多；長篇解說（90 分鐘的「深度解讀」）若標題沒有任何解說字眼，會被當成正片。寧可多放進「可能不完整」。

## 9. B 站拒絕查詢時的處理（不繞過）

現況：被拒絕就停手，結果標「可能不齊全」。新增兩件事：

1. **一鍵連結**：結果不齊全時，畫面列出這次被跳過的查詢，各附「在 B 站打開這個搜尋」的連結（B 站自己的搜尋頁網址，帶好關鍵字、時長 60 分鐘以上、按播放量排序）。使用者用自己的 B 站 App／瀏覽器打開，自己看。
2. **背景慢慢補齊**：被跳過的查詢排進佇列，工具在背景每隔一段時間（預設 3 分鐘）補查**一個**；補到就併入該次搜尋結果並更新快取。
   - 上限：每個被跳過的查詢最多重試 3 次；又被拒絕就把間隔加倍；整個佇列最多同時記 20 個查詢，滿了丟最舊的。
   - 使用者正在搜尋時，背景補齊讓路（共用同一把鎖，前景優先）。
   - 畫面：不齊全的結果顯示「正在背景補齊，剩 N 個查詢」；頁面每 60 秒自動向本機服務問一次有沒有更新（只問本機，不會多打 B 站），有新結果就更新列表。
   - 程式關掉佇列就沒了，不存檔。

這兩項都是〔我的決定〕，使用者未反對。

## 10. 怎麼做（〔我的決定〕）

- 沿用現有技術：Python／FastAPI／httpx、單一靜態頁面、pytest。
- 新增模組，各自單一職責：
  - `app/tmdb.py`：TMDB 客戶端（片單、即將上線、平台代號查詢），含快取（片單 6 小時）。
  - `app/config.py`：讀 `config.local.toml`。
  - `app/movie_classifier.py`：電影判斷，純邏輯；與 `classifier.py` 共用關鍵字與標籤工具。
  - `app/backfill.py`：補齊佇列與背景工作。
- 修改：`pipeline.py`（電影搜尋流程、記錄被跳過的查詢）、`server.py`（片單接口、搜尋接口加類型與片長參數、補齊狀態）、`index.html`（新分頁、劇／電影切換、補齊提示與一鍵連結）。
- 測試：TMDB 一律用假回應；電影判斷用固定樣本；補齊用假時鐘。不對真實 TMDB／B 站跑自動測試。拿到金鑰後做一次人工實測，並把第 5 節標〔待驗證〕的項目確認或改寫。
